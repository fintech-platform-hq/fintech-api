# Lenver Backend

The NestJS and PostgreSQL backend for Lenver, a personal finance project. The API uses authenticated, idempotent financial writes and explicit ownership checks.

## Hosted service

**Base URL**

```text
https://fintech-api-87yw.onrender.com
```

The existing Render hostname and the service identifier in the response are part of the current deployment. The examples below show the response format.

**Service status**

```bash

```

```json

  "name": "lenver-api",
  "status": "running"
}
```

**Health check**

```bash

```

## Current Scope

The API provides:

- Transaction creation with PostgreSQL persistence
- Email/password authentication with 15-minute HS256 access tokens
- Sign in with Apple through `POST /auth/apple`, issuing the same Lenver session contract
- Explicit Apple identity linking through `POST /auth/apple/link` for password-origin sessions
- Opaque 30-day refresh tokens with rotation and reuse-family revocation
- User-owned accounts and optional categories enforced by PostgreSQL constraints
- Idempotent writes using the `Idempotency-Key` header
- Conflict detection when a key is reused with a different payload
- Atomic persistence of transaction and idempotency records
- Structured request and error logging
- Request correlation through `X-Request-Id`
- Docker-based local environment
- [OpenAPI 3.1 contract](./openapi.yaml) for the current public API

The published source includes the I1–I5 MVP account endpoints for a BRL opening balance, revisioned history, dated balance checks, retroactive expense recovery, and audited corrections. See the [OpenAPI contract](./openapi.yaml) for the endpoints in your checkout. Deployment, legacy-data adoption, and operation against a live database require separate verification.

### Sign-in method operation receipts

OpenAPI 1.1.0 adds an optional UUID `Idempotency-Key` to Apple link/unlink,
password link confirmation and password unlink. Use a new UUID for each
deliberate change. Query `GET /v1/auth/method-operations/{operationId}` with
the same holder's active session family after a response is lost. An absent
receipt returns `unknown` and never replays the command. Use a password
session for a receipt-tracked Apple unlink so that the initiating family
remains usable.

Upgrade the schema in order using the tracked migrations. The receipt
migration requires `20261127_v1` and advances the readiness marker to
`20261127_v1_method_receipts`. Rehearse migration and verify the target
runtime role can read and insert method receipts before connecting this
candidate to an existing database.

## Why Idempotency Matters

Financial clients often retry requests when a response is delayed or a connection is interrupted. Without idempotency protection, the same logical operation could be persisted more than once.

This API requires an `Idempotency-Key` for transaction creation and handles repeated requests as follows:

| Request                        | Result                                                        |
| ------------------------------ | ------------------------------------------------------------- |
| New key and valid payload      | Creates the transaction and returns `201 Created`             |
| Same key and same payload      | Returns the original transaction without creating a duplicate |
| Same key and different payload | Rejects the request with `409 Conflict`                       |

The API generates a deterministic hash from the request payload. The hash is stored with the idempotency record and used to distinguish a legitimate retry from conflicting key reuse.

The transaction and its idempotency record are persisted inside the same PostgreSQL transaction. A failure rolls back both operations.

`clientMutationId` is a required UUID generated by the client for one logical operation. It is part of the complete payload hash and must remain unchanged on every retry made with the same `Idempotency-Key`. The legacy `POST /transactions` path uses the idempotency key as the database uniqueness boundary. The revisioned MVP endpoint has its own documented contract.

## API

### List accounts

```http
GET /accounts
```

The endpoint requires a Bearer access token and returns only accounts owned by
the authenticated user. A user without accounts receives `200` with `[]`.

```json
[
  {
    "id": "10000000-0000-4000-8000-000000000001",
    "name": "Main",
    "currency": "BRL",
    "createdAt": "2026-09-10T15:00:00.000Z"
  }
]
```

The public response never includes `userId`.

### Create an account

```http
POST /accounts
```

```json
{
  "name": "Main",
  "currency": "BRL"
}
```

The authenticated principal determines ownership. `userId` is not accepted in
the request. Leading and trailing whitespace in `name` is removed before the
account is persisted. The current MVP accepts only `BRL`; the operation creates
only an account and does not create categories or transactions. A successful
request returns `201` with `id`, `name`, `currency`, and `createdAt`.

### Create a transaction

Use `expense` for an outgoing amount and `income` for an incoming amount.
The legacy values `debit` and `credit` are rejected with `400 Bad Request`.

```http
POST /transactions
```

#### Headers

```http
Content-Type: application/json
Authorization: Bearer <access-token>
Idempotency-Key: <uuid>
```

#### Example request

```bash
curl -i \
  -X POST https://fintech-api-87yw.onrender.com/transactions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <access-token>" \
  -H "Idempotency-Key: 00000000-0000-4000-8000-000000000004" \
  -d '{
    "accountId": "00000000-0000-4000-8000-000000000001",
    "categoryId": "00000000-0000-4000-8000-000000000002",
    "type": "income",
    "amountMinor": 15000,
    "currency": "BRL",
    "description": "Salary",
    "occurredAt": "2026-07-30T18:00:00.000Z",
    "clientMutationId": "00000000-0000-4000-8000-000000000003"
  }'
```

`amountMinor` is expressed in the currency's minor unit. For example, `15000` represents `R$ 150,00` when the currency is `BRL`.

The account and optional category must belong to the authenticated user. Transaction currency must equal account currency. Missing and foreign-owned resources both return `404` to avoid exposing ownership information. Idempotency keys are scoped by authenticated user.

#### Example response

```json
{
  "id": "6aef7ec3-58fb-4ac7-8ff2-920e90ce0b4c",
  "accountId": "00000000-0000-4000-8000-000000000001",
  "categoryId": "00000000-0000-4000-8000-000000000002",
  "type": "income",
  "amountMinor": 15000,
  "currency": "BRL",
  "description": "Salary",
  "occurredAt": "2026-07-30T18:00:00.000Z",
  "createdAt": "2026-07-30T18:00:01.421Z"
}
```

### Replay the same request

Send the same payload using the same idempotency key:

```bash
curl -i \
  -X POST https://fintech-api-87yw.onrender.com/transactions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <access-token>" \
  -H "Idempotency-Key: 00000000-0000-4000-8000-000000000004" \
  -d '{
    "accountId": "00000000-0000-4000-8000-000000000001",
    "categoryId": "00000000-0000-4000-8000-000000000002",
    "type": "income",
    "amountMinor": 15000,
    "currency": "BRL",
    "description": "Salary",
    "occurredAt": "2026-07-30T18:00:00.000Z",
    "clientMutationId": "00000000-0000-4000-8000-000000000003"
  }'
```

The API returns the transaction associated with the original request instead of inserting a second record.

### Test conflicting key reuse

Reuse the same key with a modified payload:

```bash
curl -i \
  -X POST https://fintech-api-87yw.onrender.com/transactions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <access-token>" \
  -H "Idempotency-Key: 00000000-0000-4000-8000-000000000004" \
  -d '{
    "accountId": "00000000-0000-4000-8000-000000000001",
    "categoryId": "00000000-0000-4000-8000-000000000002",
    "type": "income",
    "amountMinor": 25000,
    "currency": "BRL",
    "description": "Salary",
    "occurredAt": "2026-07-30T18:00:00.000Z",
    "clientMutationId": "00000000-0000-4000-8000-000000000003"
  }'
```

The API rejects the request with:

```http
HTTP/1.1 409 Conflict
```

Use a new idempotency key when repeating these examples after the first successful request.

## Request Correlation and Logging

Every response receives a new server-generated UUID in `X-Request-Id`. The current middleware does not propagate a client-supplied `X-Request-Id`; any inbound value is ignored.

For example:

```bash
curl -i \
  https://fintech-api-87yw.onrender.com/health
```

Structured logs include:

- Request ID
- HTTP method
- Request path
- Response status
- Request duration
- Error context when a request fails

This makes it possible to correlate client errors with backend events without relying on unstructured console messages.

## Architecture

The codebase follows NestJS module boundaries while keeping persistence behavior explicit.

```text
src/
├── app.controller.ts
├── app.module.ts
├── main.ts
├── common/
│   ├── database/
│   └── logging/
└── modules/
    ├── auth/
    └── transactions/
```

### Request flow

```text
HTTP request
    │
    ▼
Transactions Controller
    │
    ▼
Validation and application logic
    │
    ▼
PostgreSQL transaction
    ├── Check idempotency key
    ├── Compare request hash
    ├── Insert financial transaction
    └── Store idempotency response
```

The project currently uses explicit SQL through `pg` rather than an ORM. This keeps transaction boundaries, locking behavior, constraints, and rollback semantics visible in the implementation.

- Node.js
- npm

### Install dependencies

```bash
npm install
```

### Environment configuration

Configure these variables for the local process or Docker Compose. Use a local PostgreSQL connection string and local credentials:

```env
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/fintech
JWT_ACCESS_SECRET=<at-least-32-characters-from-a-secret-store>
JWT_ISSUER=fintech-api
JWT_AUDIENCE=fintech-clients
LENVER_APPLE_ENVIRONMENT=staging
APPLE_CLIENT_ID=com.ferrari.lenver.staging
APPLE_TEAM_ID=<10-character-team-id>
APPLE_KEY_ID=<10-character-key-id>
APPLE_PRIVATE_KEY_P8=<secret-managed-private-key>
APPLE_REFRESH_TOKEN_ENCRYPTION_KEY=<unpadded-base64url-32-byte-key>
PORT=3000
```

For production, pair `LENVER_APPLE_ENVIRONMENT=production` with
`APPLE_CLIENT_ID=com.ferrari.lenver` and the Apple signing key for that App ID.
Use the existing database, JWT and refresh-token encryption configuration for
each environment. After building, run `npm run preflight:config` in the target
environment to check local configuration. It reports booleans and makes no
database or Apple requests.

Apple configuration is loaded when Apple sign-in, linking, or an Apple refresh
whose provider validation is at least 24 hours old requires it. Temporary failures
return `503` without consuming the Lenver refresh token, with a 60-second
process-local backoff; see the [Apple contract](docs/specs/apple-authentication.md).
Do not commit real credentials,
encryption keys, or production connection strings.

### Start with Docker

The checkout builds `lenver-api:local` and uses containers `lenver-api` and
`lenver-postgres`. Keep the Compose project name used by your existing checkout
to retain its `postgres_data` volume. The database is still named `fintech`.

```bash
docker compose up --build
```

If another PostgreSQL already uses host port `5432`, set
`LENVER_POSTGRES_HOST_PORT=5433` for the Compose command. The API still connects
to `postgres:5432` inside Compose. Clients running on the host, including a
locally started API, must use the selected host port in `DATABASE_URL`.

## Error Handling

The API returns consistent HTTP errors for invalid or conflicting requests.

Relevant transaction responses include:

| Status                      | Meaning                                         |
| --------------------------- | ----------------------------------------------- |
| `201 Created`               | Transaction created successfully                |
| `400 Bad Request`           | Invalid input or missing required data          |
| `401 Unauthorized`          | Missing, invalid, or expired authentication     |
| `404 Not Found`             | Resource unavailable to the authenticated user  |
| `409 Conflict`              | Idempotency key reused with a different payload |
| `429 Too Many Requests`     | Authentication endpoint rate limit exceeded     |
| `500 Internal Server Error` | Unexpected server or persistence failure        |

Errors retain the current NestJS envelope. Validation failures may contain an array of messages:

```json
{
  "statusCode": 400,
  "message": ["accountId must be a UUID"],
  "error": "Bad Request"
}
```

`POST /transactions` derives identity only from the validated JWT `sub`; identity fields supplied through the payload are rejected.

Internal errors are logged with request context. Infrastructure details and sensitive database information are not intended to be exposed in client responses.

## Design Decisions

### Store monetary values as integers

Transaction amounts are represented in minor units rather than floating-point values.

```text
R$ 150,00 → 15000
```

This avoids floating-point precision errors in financial calculations.

### Keep idempotency inside PostgreSQL

The transaction and its idempotency result are committed atomically in the same database transaction. The API cannot persist one without the other.

Redis may be introduced later for distributed coordination and caching, but it is not treated as the source of truth for the current implementation.

### Use database constraints as a final safeguard

Application checks improve error handling, while PostgreSQL constraints protect persisted data from invalid or duplicated states.

### Use explicit SQL transaction boundaries

The current implementation favors visible transaction control over ORM abstractions. This makes commit, rollback, locking, and failure behavior easier to inspect during this stage of development.

## Current Limitations

This repository is under active development. The current version does not yet include:

- Redis integration
- Automated GitHub Actions checks
- Concurrency stress-test coverage
- Production-grade readiness checks for external dependencies

`GET /health` currently verifies that the application process is responding. It does not yet confirm database readiness.

Authentication endpoints use process-local, per-IP rate limits: register/login allow 5 requests per 15 minutes, refresh allows 10, and logout allows 30. This is intentionally limited to the current single-instance architecture and must move to shared storage before scale-out.

## Roadmap

Legacy-data adoption requires validation of ownership, compatibility, and active writers. CI, shared rate limiting before scale-out, and separate readiness probes remain engineering follow-ups.
